Notes & tradeoffs — legend chip + always-expanded buttons

  • Why book-open for the chip. Lucas picked this from the Polaris IconType union. Semantically reads as "reference / look up what these mean" — matches the chip's purpose. Verified to exist in node_modules/@shopify/polaris-types/dist/polaris.d.ts. Render via <s-icon type="book-open" size="small">.
  • The literal word "Legend" stays on the chip. Icon alone is discoverable but ambiguous (could read as "open documentation"). The word "Legend" pinned next to the icon disambiguates and is bilingual-friendly via map.legend.chipLabel ("Legend" / "Legenda").
  • Why hover/focus + pure CSS, not a Polaris <s-popover>. The popover needs to open on hover (Polaris popovers are click-toggle). Pure CSS :hover + :focus-within is the same pattern already used by the existing six pills (.legendPill:hover .legendPillText) — consistent with what's there, no new component. Keyboard users tab to the chip; :focus-within + tabindex="0" on the chip keeps the popover open while focus is anywhere inside.
  • Why the chip uses :focus-within not :focus. Some assistive-tech focus rings land on individual popover items. :focus-within on the outer chip element keeps the popover open as focus moves between the chip and its items.
  • Popover position: above the chip (bottom-up). The meta row sits at the bottom of the map block. Anchoring above keeps the popover from being clipped by anything below. bottom: calc(100% + 8px); left: 0; aligns the popover to the chip's left edge so it visually "grows up" from the trigger.
  • Mobile. Hover doesn't exist on touch. :focus-within still fires on tap (chip is tabindex="0"). Tapping the chip focuses it → popover opens; tap elsewhere → blur → popover closes. Acceptable. If iOS Safari blur quirks surface, fall back to a click-toggle backed by a small useState — but try CSS-only first.
  • Always-expanded buttons. Drop .hoverExpandWrap / .hoverExpandLabel usage in the control-row buttons; render <s-button> with icon + label inline. The CSS classes can stay (used elsewhere) but the route stops applying them to the control cluster. Reassign-popover trigger keeps the popover affordance, just no longer hidden behind a hover label.
  • What this fixes operationally. Three regressions reported since the hover-expand shipped: (1) operators not realizing what each icon means until they hover — slow scanning; (2) on touch laptops, hover-discoverability is unreliable; (3) screen-readers announce the button without context until tabbed-into. Always-expanded labels solve all three.
  • What this does NOT change. The Reassign-to ▾ popover (the route-target picker that's the subject of this branch's other fix) stays a click-popover, not hover. Same for ⋯ More actions. Only the legend trigger gets the hover-expand pattern.
  • i18n keys to add. map.legend.chipLabel (en: "Legend" / pt-BR: "Legenda"). The six legend item labels (map.legend.failed, .overdue, .dueToday, .dueTomorrow, .dueLater, .addressError) already exist and are reused inside the popover.

⚠ Canonical bug — State C

  • Symptom: Confirm button visible when user has selected assigned stops in edit mode but has not yet committed any Reassign/Unassign — there is nothing to confirm.
  • Contract: matrix-row C → Confirm = hid. Confirm only renders when at least one route is dirty (dirtyRouteIds.size > 0).
  • Likely root cause (to be traced during implementation): dirtyRouteIds is being populated as a side effect of click-to-enter-edit (rev 21) instead of only by Reassign/Unassign commits. The fix is upstream of showConfirm; the gate at line 5903 is correct.
  • Why hide and not disable: per CLAUDE.md → "Control Panels & State-Driven Visibility", compact panels follow an "only actionable controls are visible" premise. A disabled Confirm here would tell the user "this panel exists to confirm something," which is misleading — the panel's purpose at this moment is to let them choose Reassign / Unassign / Clear, not Confirm.

Location === "all" — selection gate (page-level)

When the Location filter is set to "all" (the default first-load state, DEFAULT_LOCATION_ID on line 47), the routing flow has no origin location, so selecting orders does nothing. The control row already hides itself (line 5881 if (!isLocationContext) return null), but selection is still reachable from two surfaces: the All-orders table checkboxes (rows 3561 / 3609) AND the map markers (click handlers at lines 1691, 1722). Both surfaces register the selection and silently drop it. Ghost affordances on both ends.

Fix — three prongs, one banner:

  • (a) Page-level info banner placed just below the Location filter (above the map), so it's the first thing the user sees when location === "all". Single source of truth for the explanation.
  • (b) Hide the All-orders checkbox column entirely. Conditional grid template.
  • (c) Disable map-marker click handlers when location === "all" — clicking does nothing. No edit-mode entry, no toggleSelection, no ghost selection. The banner is the explanation.

Notes & tradeoffs — page-level location gate

  • Why ONE banner, not two. A second banner above the table would duplicate the message. The page-level banner above the map is in view when the user lands; the table is below, so by the time they reach it they've already passed the banner. Single explanation = single source of truth.
  • Layout shifts on filter change. When the user picks a specific location, the banner disappears and the checkbox column reappears (28px shift). One-time shift on a deliberate filter change, not a layout flicker mid-interaction. Acceptable.
  • Banner tone. info, not warning. The user isn't doing anything wrong; they just haven't picked a location yet.
  • Banner copy mentions BOTH gated surfaces. "Until then, map markers and order selection are read-only" tells the user upfront that clicking won't do anything, so the silent no-op on map clicks doesn't feel like a bug.
  • i18n. Banner keys: map.locationGate.banner.heading + .body (en + pt-BR). The body string includes the "map markers and order selection are read-only" clause.
  • Map-marker visual treatment. No greying-out, no opacity reduction. The marker colors encode order urgency (Today / Tomorrow / Later / Address-error) — that information stays valuable even when clicks are gated. Don't kill the signal to soften the affordance.
  • Where the click-disable lives in code. Click handlers at app/routes/app.local-delivery.tsx lines 1691 and 1722. Wrap the existing handler bodies in if (locationId === DEFAULT_LOCATION_ID) return; as the first statement. Equivalent to the control-row guard at line 5881.
  • Banner-only fallback (rejected). Originally considered keeping checkboxes + click handlers functional plus a banner. Rejected — creates a "click does nothing" feedback gap that violates the "only actionable controls are visible" premise. Hide-don't-disable applies symmetrically across all surfaces.
  • Implementation hint — table grid. The table grid template uses grid-template-columns: 24px ... when checkbox is present. Extract to a variable derived from locationId !== DEFAULT_LOCATION_ID; conditionally render the header/row checkbox cells too.

Notes & tradeoffs — Exit confirmation

  • State B is the exception. When edit mode is active but no changes are pending and no selection exists, Exit fires immediately with NO modal — there's nothing to lose. The matrix encodes this as vis · imm.
  • Button order. Secondary Stay on the LEFT, primary critical Discard and exit on the RIGHT — matches CLAUDE.md → "Buttons" rule (rightmost = primary). Critical-tone primary because the action is destructive.
  • Discard verb. Chose Discard and exit over Exit without saving because the user never explicitly "saved" anything — they committed Reassign/Unassign locally; nothing has hit the server. "Discard" reads as "throw away local edits", which is accurate.
  • Modal also when Esc / backdrop? No — Esc and backdrop click should be treated as Stay (non-destructive default). The modal uses commandFor + command="--hide" on the Stay button only; the Discard button calls cancelPolylineEditMode() programmatically.
  • i18n. Two key groups: map.polylineEdit.exitConfirm.heading + .body (D/D') and map.polylineEdit.exitConfirmAfterError.heading + .body (G). Plural-aware count formatting needed ({{N}} pending route change(s)).
  • Plural rule. When N=1, body reads "your 1 pending route change". When N≥2, "your {{N}} pending route changes". Use existing i18n plural infrastructure.
