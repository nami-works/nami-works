Mockup notes (delete in production)

  • Data source: reads from RouteOptimizationDecision (Phase 1.6 Prisma model). Filters compose into a WHERE clause; pagination is offset-based, 20 rows per page.
  • Filters: Period (last 7 / 30 / quarter), Location, plus filter chips (All / Unreviewed / Wrong calls / Clean). Chips drive operatorReviewed + operatorVerdict filtering; counts reflect current period + location scope.
  • Status chips on rows: derived from decisionPath + postMortemFlags[] + operatorReviewed. A row CAN have multiple (e.g. "auto-dispatched" + "post-mortem flag" + "unreviewed"). Cap visible chips at 3; rest available in detail.
  • 2-column layout (mirrors local-delivery) with drill-down on selection: Main area always holds the map (or an empty placeholder when nothing is selected). Aside default state holds the list of decisions. Clicking a row drills down — URL gains ?selected=<id>, the OTHER rows are suppressed (aside renders only the selected decision's detail), and a back-row appears at the top with three control groups: back link · paginator · primary action. Back button clears ?selected=. Mobile (≤1100px) collapses to single column, map first then aside.
  • Paginator (filter-aware): Compact triad ‹ N of total › in the center of the back-row. N and total are computed over the current filtered list at click time, not the global decision set. On "Unreviewed" filter with 12 items, counter reads "3 of 12"; after approving the current one, the list refreshes and counter becomes "3 of 11" pointing at the new 3rd item (operator never goes backward through reviewed work). Prev/next disabled (greyed, no hover) at boundaries — first decision disables prev, last disables next, single-item disables both. Hover-tooltip shows the active filter: "Filter: Unreviewed".
  • Auto-next on both verdict paths: Top "Mark approved" AND bottom form's "Save verdict" both submit + auto-load the next decision in the filtered list. Same end behavior. If there's no next (last in filter), navigate back to the list view and render a success toast banner at the top: "All caught up. Every decision in this view has been reviewed." List itself shows all chips green for that filter. Switching to "All" filter restores the historical browse.
  • "Mark approved" backend trigger: Single DB write — UPDATE RouteOptimizationDecision SET operatorReviewed=true, operatorVerdict='correct', operatorComment=NULL, updatedAt=NOW() WHERE id=$1 AND shop=$2. No dispatch mutation, no LLM call, no webhook, no notification. Log line tagged via=fast-pass for later analytics.
  • Top-right element lifecycle: The button on the right of the back-row changes over the decision's review lifecycle:
    1. Unreviewed → [Mark approved] primary button (fast-pass for verdict=correct).
    2. Click Mark approved or Save verdict → submits + auto-navigates to next decision in the filter. No "Saved ✓" state in-place — the operator's already on the next item.
    3. Revisiting a reviewed decision, no edits → subdued Reviewed badge (gray pill, not clickable). Header chip carries the actual verdict (reviewed · correct / · wrong call / · edge case).
    4. Operator edits the form (changes radio or comment) on a reviewed decision → badge transforms back into a [Save changes] primary button. Header gains an unsaved edits amber chip. The form's Save verdict button at the bottom also reappears. Both buttons submit the same form.
  • Dirty-state guard (unsaved-changes modal): When the form is dirty (Variant F state) and the operator clicks any navigation control (back, prev, next, a filter chip, the browser back button), a modal blocks the navigation. Three options: Save & continue (submit then navigate to the intended target), Discard changes (navigate, lose edits), Cancel (close modal, stay on current decision). Page refresh falls back to the native browser dialog. Save changes and Save verdict buttons in the dirty state do NOT trigger the modal — they're the explicit save path.
  • URL state: Every navigation updates ?selected=<id> in place. Browser back/forward work naturally; a specific decision is shareable via copy-link; mid-review refresh preserves position.
  • In-progress verdict-form draft preservation across paginator navigation: NOT preserved in MVP. If operator picks "Wrong call" + types a reason but clicks paginator before saving, the text is lost. The auto-next on Save makes this rare in practice. Add sessionStorage keyed by decisionId if it bites; defer.
  • Keyboard shortcuts (deferred): ←/→ prev/next, A approve, Esc back. Ship after the mouse flow is validated.
  • Verdict workflow: state matrix at top governs. "Save verdict" hidden until radio picked; disabled-with-tooltip when comment required but missing. Posts to /api/control/post-mortem-verdict with body {decisionId, verdict, comment}; success flips the button to "Saved ✓" and adds the chip on the list row.
  • CLI parity: nami_control.py post-mortem-list + post-mortem-verdict --decision-id <id> --verdict wrong-call --reason "..." mirror the UI for headless use.
  • Rule-promotion-gate hook: 3 same-direction wrong calls within 90 days OR 5 across tenants triggers an operator notice ("This pattern keeps surfacing; propose a registry update?"). Future Phase 4 work — out of scope for this PR.
  • Polaris translation: rows → custom div + click handler (no <s-resource-list> — too rigid for our chip-heavy layout). Filter selects → <s-select> with external label pattern. Map frame → Google Static Maps PNG fetched via the same builder used by handleRenderRoutes (server-side fetch, base64-encoded into the response; client receives a data URL). Detail aside → custom sticky div (Polaris <s-modal> would over-promise the close-button + escape semantics; sticky aside is closer to how local-delivery's route-manager cards behave).
