Loyalty customer block — mockup v1

Shopify Admin UI Extension that renders inline on the customer-detail page (target admin.customer-details.block.render). Two-tier disclosure: operator view (default) carries only what GE Beauty support staff need to help a customer redeem; analyst view (collapsed) carries full test context for Lucas and test owners. Bilingual: PT-BR primary, EN shown below each panel for review purposes (production renders one language based on admin user locale).

Design decisions baked into this mockup

  • Two-tier disclosure — operator section above, "Mais detalhes / More details" expander below revealing the analyst section. No access gating: operators technically can expand, but the test-context language won't make them act differently.
  • Operator-language rules — no occurrences of "test", "arm", "cohort", "tranche", or "enrollment" in the operator section. Verified across all 4 base states + 4 edge cases.
  • Partial-redemption display — "Remaining + already used" two-line treatment per Lucas's 2026-05-16 call (e.g. "R$25 de crédito disponíveis. R$15 já utilizados.").
  • Near-expiry urgency — yellow callout block around the expiry line when ≤7 days remain. Single tier, no escalating red. Renders as a Polaris-style notice strip, not a banner.
  • Cancelled-by-refund — operator sees "Bônus removido porque o pedido #X foi reembolsado em [data]" for the 90 days the bonus would have been active. Auto-converts to "Sem bônus ativo" after that window.
  • Just-expired (≤48h) — operator sees "Este bônus expirou em [data]" with subdued/italic treatment for 24-48h. Auto-converts to "Sem bônus ativo" after the grace window.
  • Money format — BRL with R$ prefix, integer values (R$32, not R$32,00). Matches Polaris `formatCurrency` BRL output.
  • Date format — ISO-style (2026-08-15) for the mockup. Production renders user-locale-aware via `Intl.DateTimeFormat`.
  • Discount codes — rendered as monospace pills (visual nod to "this is a copyable token"). Match Polaris discount-code styling.
  • Expanded analyst section — labelled "Test cohort: Arm A — tapering cashback" etc. Includes enrolled order with deep-link to the order page, decay schedule with current-window highlighted, redemption history.
  • Out of scope (per integrations-engineer brief) — no Force-redeem / Force-cancel action buttons. Read-only MVP.

Every meaningful state the block can be in, with the operator-section behavior pinned per state. Future sessions reading this design should see what each state was supposed to do, not just the happy path. Rows correspond to the rendered mockups below.

States deferred (narrow / can resolve with reasonable defaults)

  • Redemption in flight (order placed, paid webhook hasn't fired yet) — block shows the current state. UI refreshes when next loaded. Acceptable race window.
  • Multiple concurrent enrollments — prevented by the active-enrollment guard in the enrollment trigger (per /integrations-engineer brief). Should be impossible; if it happens, block shows the earliest active and logs a warning.
  • Customer in pre-test period (existing CRM Bonus code still valid, never enrolled in new test) — block shows "Sem bônus ativo no momento" since CRM Bonus codes live OUTSIDE our LoyaltyEnrollment table. Customer's existing CRM Bonus code is still usable at checkout; just invisible to this block. Acceptable for pilot — if Lucas wants to show legacy codes in this block too, that's a v2.

Cap math

On a R$220 order, 20% would discount R$44 but the 25% cart cap kicks in at R$55, so the cap is not binding. On a R$150 order, 20% would discount R$30 (under the R$37.50 cap, also not binding). The cap only matters for orders below ~R$80, where 20% would exceed 25% of the cart.
